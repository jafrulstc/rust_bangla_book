# Writing Automated Tests

১৯৭২ সালের তাঁর "The Humble Programmer" প্রবন্ধে Edsger W. Dijkstra বলেছিলেন, "program testing খুব কার্যকরী উপায়ে bug-এর উপস্থিতি দেখাতে পারে, কিন্তু bug-এর অনুপস্থিতি প্রমাণ করতে এটি একেবারেই অক্ষম।" এর মানে এই নয় যে আমরা যতটা সম্ভব পরীক্ষা করার চেষ্টা করব না!

আমাদের program-গুলোর _correctness_ (শুদ্ধতা) বলতে বোঝায় আমাদের code যথেষ্ট পরিমাণে সেটাই করছে যা আমরা চাই। Rust এমনভাবে ডিজাইন করা হয়েছে যাতে program-এর correctness-এর প্রতি গভীর যত্ন নেওয়া হয়, কিন্তু correctness একটি জটিল বিষয় এবং প্রমাণ করা সহজ নয়। Rust-এর type system এই দায়িত্বের বড় একটা অংশ নিজের কাঁধে নেয়, কিন্তু type system সবকিছু ধরতে পারে না। এই কারণেই Rust-এ automated software test লেখার সুবিধা রয়েছে।

ধরো আমরা একটি `add_two` ফাংশন লিখলাম যেটাতে যেই সংখ্যাই পাস করা হোক না কেন তার সাথে 2 যোগ করে। এই ফাংশনের signature একটি পূর্ণসংখ্যাকে parameter হিসেবে গ্রহণ করে এবং একটি পূর্ণসংখ্যা result হিসেবে ফেরত দেয়। যখন আমরা এই ফাংশনটি implement ও compile করি, তখন Rust সেই সব type checking ও borrow checking করে যা তুমি এ পর্যন্ত শিখেছো — যাতে নিশ্চিত হওয়া যায় যে, উদাহরণস্বরূপ, আমরা এই ফাংশনে কোনো `String` value বা অগ্রহণযোগ্য reference পাস করছি না। কিন্তু Rust _পারে না_ যাচাই করতে যে এই ফাংশনটি ঠিক সেটাই করছে যা আমরা চাই — অর্থাৎ parameter-এর সাথে 2 যোগ করে ফেরত দিচ্ছে, না পারে parameter-এর সাথে 10 যোগ করছে বা 50 বিয়োগ করছে! এখানেই test-গুলো কাজে আসে।

আমরা এমন test লিখতে পারি যেগুলো assert করে, উদাহরণস্বরূপ, যে `add_two` ফাংশনে `3` পাস করলে ফেরত আসা value `5` হবে। আমরা যখনই আমাদের code-এ কোনো পরিবর্তন করি, এই test-গুলো চালাতে পারি যাতে নিশ্চিত হই যে আগে থেকে থাকা কোনো সঠিক আচরণ পরিবর্তিত হয়নি।

Testing একটি জটিল দক্ষতা: যদিও একটি chapter-এ ভালো test লেখার প্রতিটি বিস্তারিত বিষয় আমরা শেষ করতে পারব না, তবু এই chapter-এ আমরা Rust-এর testing সুবিধাগুলোর কার্যপ্রণালী নিয়ে আলোচনা করব। আমরা test লেখার সময় তোমার ব্যবহারযোগ্য annotation ও macro, test চালানোর জন্য প্রদত্ত default আচরণ ও option, এবং test-গুলোকে কীভাবে unit test ও integration test-এ সাজাতে হয় সে সম্পর্কে কথা বলব।
