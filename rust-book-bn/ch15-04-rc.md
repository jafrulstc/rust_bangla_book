## `Rc<T>`, Reference-Counted Smart Pointer

বেশিরভাগ ক্ষেত্রে, ownership স্পষ্ট থাকে: তুমি ঠিক জানো কোন variable একটি নির্দিষ্ট value-কে own করে। তবে এমন ক্ষেত্র আছে যখন একটি single value-এর একাধিক owner থাকতে পারে। উদাহরণস্বরূপ, graph data structure-এ, একাধিক edge একই node-কে point করতে পারে, এবং সেই node-টি ধারণাগতভাবে যারা তাকে point করে সব edge-এর own। এমন কোনো node পরিষ্কার করা উচিত নয় যদি না তার কোনো edge pointing না থাকে, অর্থাৎ কোনো owner না থাকে।

তোমাকে Rust type `Rc<T>` ব্যবহার করে multiple ownership explicitly সক্ষম করতে হবে, যা _reference counting_-এর abbreviation। `Rc<T>` type একটি value-এর reference সংখ্যা track রাখে যাতে নির্ধারণ করা যায় value-টি এখনো ব্যবহৃত হচ্ছে কি না। যদি কোনো value-এর শূন্যটা reference থাকে, তবে সেই value-টি পরিষ্কার করা যেতে পারে এবং কোনো reference invalid হবে না।

`Rc<T>`-কে একটি family room-এর TV হিসেবে কল্পনা করো। যখন একজন মানুষ TV দেখতে ঢোকে, সে সেটি on করে। অন্যরা ঘরে এসে TV দেখতে পারে। যখন শেষ ব্যক্তি ঘর ছেড়ে যায়, সে TV off করে দেয় কারণ সেটি আর ব্যবহৃত হচ্ছে না। যদি কেউ অন্যরা এখনো দেখছে তখনই TV off করে দেয়, তাহলে বাকি TV দর্শকদের কাছ থেকে প্রতিবাদ উঠবে!

আমরা `Rc<T>` type ব্যবহার করি যখন আমরা কিছু data heap-এ allocate করতে চাই আমাদের program-এর একাধিক অংশে read করার জন্য এবং আমরা compile time-এ নির্ধারণ করতে পারি না কোন অংশটি সর্বশেষ data ব্যবহার করবে। যদি আমরা জানতাম কোন অংশটি সর্বশেষ ব্যবহার করবে, তাহলে আমরা শুধু সেই অংশটিকে data-এর owner বানাতে পারতাম, এবং compile time-এ enforce করা স্বাভাবিক ownership rule গুলো কার্যকর হতো।

মনে রাখবে `Rc<T>` শুধুমাত্র single-threaded scenario-তে ব্যবহারের জন্য। Chapter 16-এ concurrency নিয়ে আলোচনা করার সময় আমরা multithreaded program-এ কীভাবে reference counting করতে হয় তা দেখব।

### Data Share করা

চলো Listing 15-5-এর আমাদের cons list উদাহরণে ফিরে যাই। মনে করো আমরা এটি `Box<T>` ব্যবহার করে define করেছিলাম। এবার, আমরা এমন দুটি list তৈরি করব যা উভয়েই একটি তৃতীয় list-এর ownership share করে। ধারণাগতভাবে এটি Figure 15-3-এর মতো দেখাবে।

আমরা list `a` তৈরি করব যাতে `5` এবং তারপর `10` আছে। তারপর, আমরা আরও দুটি list বানাবো: `b` যা `3` দিয়ে শুরু এবং `c` যা `4` দিয়ে শুরু। `b` এবং `c` list দুটি তারপর `5` এবং `10` ধারণকারী প্রথম `a` list-এ চলে যাবে। অর্থাৎ, উভয় list-ই `5` এবং `10` ধারণকারী প্রথম list-টি share করবে।

আমাদের `List`-এর `Box<T>` সহ definition ব্যবহার করে এই scenario implement করার চেষ্টা করলে কাজ করবে না, যেমন Listing 15-17-তে দেখানো হয়েছে।

<Listing number="15-17" file-name="src/main.rs" caption="Demonstrating that we’re not allowed to have two lists using `Box<T>` that try to share ownership of a third list">

```rust,ignore,does_not_compile
enum List {
    Cons(i32, Box<List>),
    Nil,
}

use crate::List::{Cons, Nil};

fn main() {
    let a = Cons(5, Box::new(Cons(10, Box::new(Nil))));
    let b = Cons(3, Box::new(a));
    let c = Cons(4, Box::new(a));
}
```

</Listing>

`Cons` variant-গুলো তারা যে data ধারণ করে তা own করে, তাই আমরা `b` list তৈরি করলে `a` কে `b`-তে move করা হয় এবং `b` হয় `a`-এর owner। তারপর, যখন আমরা `c` তৈরি করার সময় `a`-কে আবার ব্যবহার করার চেষ্টা করি, আমরা পারি না কারণ `a` ইতিমধ্যে move হয়ে গেছে।

আমরা `Cons`-এর definition পরিবর্তন করে reference ধারণ করতে পারতাম, কিন্তু তাহলে আমাদের lifetime parameter নির্দিষ্ট করতে হতো। lifetime parameter নির্দিষ্ট করে আমরা নির্দিষ্ট করতাম যে list-এর প্রতিটি element পুরো list-টির মতো দীর্ঘ বাঁচবে। Listing 15-17-এর element এবং list-গুলোর জন্য এই ক্ষেত্রে এটি সত্য, কিন্তু প্রতিটি scenario-তে নয়।

এর বদলে, আমরা আমাদের `List`-এর definition পরিবর্তন করে `Box<T>`-এর জায়গায় `Rc<T>` ব্যবহার করব, যেমন Listing 15-18-তে দেখানো হয়েছে। প্রতিটি `Cons` variant এখন একটি value এবং একটি `List`-কে point করা `Rc<T>` ধারণ করবে। আমরা `b` তৈরি করার সময়, `a`-এর ownership নেওয়ার বদলে, `a` যে `Rc<List>` ধারণ করে সেটিকে clone করব, ফলে reference সংখ্যা এক থেকে দুইতে বাড়বে এবং `a` ও `b` উভয়েই ওই `Rc<List>`-এর data-এর ownership share করবে। আমরা `c` তৈরির সময়ও `a`-কে clone করব, reference সংখ্যা দুই থেকে তিনে বাড়বে। প্রতিবার আমরা `Rc::clone` call করলে, `Rc<List>`-এর ভেতরের data-এর reference count বাড়বে, এবং যতক্ষণ না এর শূন্যটা reference থাকে ততক্ষণ data পরিষ্কার করা হবে না।

<Listing number="15-18" file-name="src/main.rs" caption="A definition of `List` that uses `Rc<T>`">

```rust
enum List {
    Cons(i32, Rc<List>),
    Nil,
}

use crate::List::{Cons, Nil};
use std::rc::Rc;

fn main() {
    let a = Rc::new(Cons(5, Rc::new(Cons(10, Rc::new(Nil)))));
    let b = Cons(3, Rc::clone(&a));
    let c = Cons(4, Rc::clone(&a));
}
```

</Listing>

আমাদের একটি `use` statement যোগ করতে হবে যাতে `Rc<T>` scope-এ আসে কারণ এটি prelude-এ নেই। `main`-এ আমরা `5` এবং `10` ধারণকারী list তৈরি করি এবং সেটি `a`-তে একটি নতুন `Rc<List>`-এ store করি। তারপর, যখন আমরা `b` এবং `c` তৈরি করি, আমরা `Rc::clone` function call করি এবং `a`-তে থাকা `Rc<List>`-এর reference একটি argument হিসেবে pass করি।

আমরা `Rc::clone(&a)`-এর বদলে `a.clone()` call করতে পারতাম, কিন্তু Rust-এর convention হলো এই ক্ষেত্রে `Rc::clone` ব্যবহার করা। `Rc::clone`-এর implementation বেশিরভাগ type-এর `clone` implementation-এর মতো সব data-এর deep copy করে না। `Rc::clone`-এর call শুধু reference count বাড়ায়, যা বেশি সময় নেয় না। Data-এর deep copy অনেক সময় নিতে পারে। reference counting-এর জন্য `Rc::clone` ব্যবহার করে আমরা deep-copy জাতীয় clone এবং reference count বাড়ায় এমন clone-এর মধ্যে দৃশ্যত পার্থক্য করতে পারি। code-এ performance problem খোঁজার সময়, আমাদের শুধু deep-copy clone-গুলো বিবেচনা করতে হবে এবং `Rc::clone`-এর call গুলো উপেক্ষা করতে পারি।

<a id="cloning-an-rct-increases-the-reference-count"></a>

### Reference Count বাড়াতে Cloning

চলো Listing 15-18-এর কার্যকর উদাহরণটি পরিবর্তন করি যাতে আমরা `a`-তে `Rc<List>`-এর reference তৈরি এবং drop করার সময় reference count কীভাবে পরিবর্তিত হয় তা দেখতে পারি।

Listing 15-19-এ, আমরা `main`-কে পরিবর্তন করব যাতে list `c`-এর চারপাশে একটি inner scope থাকে; তারপর, আমরা দেখতে পাব যখন `c` scope ছেড়ে যায় তখন reference count কীভাবে পরিবর্তিত হয়।

<Listing number="15-19" file-name="src/main.rs" caption="Printing the reference count">

```rust
// --snip--

fn main() {
    let a = Rc::new(Cons(5, Rc::new(Cons(10, Rc::new(Nil)))));
    println!("count after creating a = {}", Rc::strong_count(&a));
    let b = Cons(3, Rc::clone(&a));
    println!("count after creating b = {}", Rc::strong_count(&a));
    {
        let c = Cons(4, Rc::clone(&a));
        println!("count after creating c = {}", Rc::strong_count(&a));
    }
    println!("count after c goes out of scope = {}", Rc::strong_count(&a));
}
```

</Listing>

program-এর প্রতিটি পর্যায়ে যেখানে reference count পরিবর্তিত হয়, আমরা reference count print করি, যা আমরা `Rc::strong_count` function call করে পাই। এই function-টির নাম `strong_count` কারণ `Rc<T>` type-এর একটি `weak_count`-ও আছে; আমরা দেখব `weak_count` কীসের জন্য ব্যবহৃত হয় [“Preventing Reference Cycles Using `Weak<T>`”][preventing-ref-cycles]<!-- ignore -->-এ।

এই code নিচেরগুলো print করে:

```console
$ cargo run
   Compiling cons-list v0.1.0 (file:///projects/cons-list)
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.45s
     Running `target/debug/cons-list`
count after creating a = 1
count after creating b = 2
count after creating c = 3
count after c goes out of scope = 2
```

আমরা দেখতে পাই যে `a`-তে `Rc<List>`-এর প্রাথমিক reference count 1; তারপর, প্রতিবার আমরা `clone` call করলে count 1 করে বাড়ে। যখন `c` scope ছেড়ে যায়, count 1 করে কমে। reference count কমানোর জন্য আমাদের কোনো function call করতে হয় না যেমন reference count বাড়ানোর জন্য `Rc::clone` call করতে হয়: `Drop` trait-এর implementation একটি `Rc<T>` value scope ছেড়ে গেলে reference count স্বয়ংক্রিয়ভাবে কমিয়ে দেয়।

এই উদাহরণে যা আমরা দেখতে পাই না তা হলো, যখন `b` এবং তারপর `a` `main`-এর শেষে scope ছেড়ে যায়, count 0 হয় এবং `Rc<List>` সম্পূর্ণভাবে পরিষ্কার হয়। `Rc<T>` ব্যবহার করে একটি single value-এর একাধিক owner থাকতে দেয়, এবং count নিশ্চিত করে যে যতক্ষণ পর্যন্ত কোনো owner বর্তমান থাকে value valid থাকবে।

immutable reference-এর মাধ্যমে, `Rc<T>` তোমাকে program-এর একাধিক অংশের মধ্যে শুধু read করার জন্য data share করতে দেয়। যদি `Rc<T>` তোমাকে একাধিক mutable reference রাখতেও দিত, তাহলে তুমি হয়তো Chapter 4-এ আলোচিত borrowing rule-গুলোর একটি লঙ্ঘন করতে: একই জায়গায় একাধিক mutable borrow data race এবং অসামঞ্জস্য ঘটাতে পারে। কিন্তু data mutate করার ক্ষমতা খুবই কাজের! পরবর্তী section-এ, আমরা interior mutability pattern এবং `RefCell<T>` type নিয়ে আলোচনা করব যা তুমি একটি `Rc<T>`-এর সাথে ব্যবহার করতে পারো এই immutability restriction নিয়ে কাজ করতে।
